# 0002: Full replication of panasonic onto cabin, rEFInd included

[Platforms › Arch Linux](../docs/platforms/arch/README.md) · accepted 2026-10-05

cabin took panasonic's whole setup, boot menu included, with GRUB kept as a fallback in the firmware menu; the cost was re-deriving every machine-specific line.

## Context

The goal: make cabin match panasonic. They are not similar machines: Intel laptop on
LVM with rEFInd and Plymouth, versus an AMD/NVIDIA desktop on plain ext4 with GRUB, two
kernels, and no battery, lid, or panel backlight.

Three scopes were on the table: user layer only (the flake), user layer plus the ly
greeter, or full replication including replacing GRUB with rEFInd.

The cautious choice was the user layer only.
cabin's boot had been broken hours earlier and its GRUB was freshly verified.
The flake is the user layer by design: `home.nix` itself states "Nix on Arch doesn't own /etc, the ESP, or the initramfs."

## Decision

I chose full replication, including rEFInd, with the risks above in view.
Two constraints attach to it:

1. **GRUB stays installed and its NVRAM entry is kept.** rEFInd becomes the default boot
   entry; GRUB remains selectable from the firmware menu.
   A rEFInd misconfiguration is then recovered by picking GRUB rather than by booting an external ISO, which this machine has already needed once.
2. **Adaptation, not copying.** Every machine-specific line must be re-derived: `root=`
   (LVM device path vs `UUID=`), microcode (`intel-ucode` vs `amd-ucode`), early-KMS
   modules (`i915` vs the four nvidia modules plus `nvidia_drm.modeset=1`), and two
   kernels plus a fallback initramfs where panasonic has one kernel and none.
   `refind_linux.conf` is generated by `refind-install` (run by `bootstrap.sh` phase 4; the
   repo's `system/99-refind.hook` re-runs it on every refind upgrade), so it picks up the
   local root automatically — panasonic's must not be copied across.

## Consequences

- `install/bootstrap.sh` refuses to run `system/plymouth-setup.sh` on non-Intel GPUs,
  because that script writes `MODULES=(i915)` with no vendor detection.
  Superseded 2026-10-05: the script is parametrised (`KMS_MODULES` etc.) and runs for
  every vendor.
- `system/nftables.conf` is **not** applied to cabin as-is; it has no SSH rule and would
  lock out remote administration.
  Superseded 2026-10-05: the ruleset allows LAN SSH via `define LAN`; `system/harden.sh` was
  applied on cabin 2026-10-06.
- The monitor identities and workspace rules in `hyprland.lua` are panasonic EDID serials
  and will need a cabin equivalent; until then the catch-all monitor rule applies and
  workspace placement is arbitrary.
  Superseded 2026-10-05: cabin has the same monitors.

## How it is checked

Nothing checks this: it records a one-time choice for a machine that was reinstalled later ([0010](0010-install-path.md), [0011](0011-disk-boot-secure-boot-snapshots.md)).
`dram doctor --boot` checks the boot chain each host has now.
